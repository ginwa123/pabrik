# Admin console

The owner of a Pabrik installation manages its accounts from here: create an
account, change its role, switch it off, and reset a password for somebody
who has lost theirs. Every workspace's machine is here too, with a resize menu
for its vCPUs, memory and storage.

The console is a static page served by the Zig backend. Running it needs no
build step, no bundler and no framework: three files and the endpoints behind
them. The stylesheet is the one thing that is compiled: Tailwind produces
`admin.css` from `admin.src.css`, and the result is committed, so the server
embeds a finished file.

```
src/apps/admin/
  index.html      the page, in Tailwind utility classes
  admin.src.css   the Tailwind input: the Kanagawa Dragon tokens + components
  admin.css       GENERATED by `pnpm run build:css`; committed, served as-is
  package.json    the CSS build (`pnpm install && pnpm run build:css`)
  admin.js        the script
  admin_page.zig  serves the three files
  admin_api.zig   the /api/admin endpoints
  admin_store.zig the reads and writes on `users`
  admin_common.zig who the owner is, and the pure helpers
  runtime.zig     the database + `--auth` switch the host installs
  mod.zig         the package's public face
  main.zig        `pabrik-admin`, the standalone program
  build.zig       its own build: `zig build run` right here
  build.zig.zon   the packages it links (SQLite, the HTTP server)
```

## The look

The console wears the desktop app's **Kanagawa Dragon** palette
(`src/apps/desktop/src/style.css`), so one installation is one product: the
same ink on dark paper, the same green for the one action on a screen, the
same muted grey for the notes.

The colours and the one animation are tokens in `admin.src.css`, so a class
name in `index.html` never carries a hex value:

```css
@theme {
  --color-dim: #12120f;      /* the page ground            */
  --color-paper: #181616;    /* the masthead               */
  --color-surface: #1d1c19;  /* a panel                    */
  --color-ink: #c5c9c5;      /* running text               */
  --color-accent: #87a987;   /* the one action             */
}
```

Edit `admin.src.css` or the utility classes in `index.html`, then:

```bash
cd src/apps/admin
pnpm install          # once
pnpm run build:css    # writes admin.css
```

`admin.css` is committed because `admin_page.zig` `@embedFile`s it: the Zig
binary has to build without Node, and a machine that runs an installation
should never need a CSS toolchain. Rebuild after any class change, or the page
serves the previous stylesheet.

## One section at a time

The console is a rail plus **one** section, not every panel at once: an
operator comes to do one thing, and a wall of counts, a form and two tables is
the opposite of that. The rail (left at desktop, two buttons on a phone) holds
the sections and the counts; each section is addressable by hash
(`/admin#accounts`, `/admin#machines`), so back/forward and a pasted link land
where they say.

- **Accounts** — the table, plus the *New account* dialog behind the one
  primary action in the masthead.
- **Machines** — every workspace's machine with its **Resize** menu. Sizes and
  the restart come from `pabrik-vmd`, so this section needs `--vmd-socket` (or
  `PABRIK_VMD_SOCKET`, or the runtime dir's socket). Without one it says why and
  offers no control.
- **Handed out** is not a section: it appears above the open one, only while a
  temporary password exists to copy.

## Opening it

The console is a program of its own. `pabrik` — the server that runs the
agents — serves none of it: no `/admin` page, no `/api/admin/*`. It links only
the SQLite package, the HTTP server package and the manager client, so it
builds in seconds:

```bash
cd src/apps/admin
zig build run -- --db ~/.config/pabrik/agent.db --port 8090 \
  --vmd-socket /run/user/$(id -u)/pabrik-vmd.sock
```

```
pabrik-admin ready
  console: http://127.0.0.1:8090/admin
  database: /home/you/.config/pabrik/agent.db
  owner: the local operator (no --auth)
  machines: /run/user/1000/pabrik-vmd.sock
```

| flag | meaning |
|---|---|
| `--db <path>` | the database to administer (default `~/.config/pabrik/agent.db`) |
| `--port <n>` | the port to listen on (default `8090`) |
| `--auth on\|off` | off (default): the local operator owns the installation. on: a `pabrik_session` cookie decides the owner |
| `--vmd-socket <path>` | the manager's socket, so Machines can list and resize. Default, in the same order the server resolves it: `$PABRIK_VMD_SOCKET`, then `$XDG_RUNTIME_DIR/pabrik-vmd.sock`, then `/tmp/pabrik-vmd.sock`. A socket nobody answers on is not fatal: the section names the path it tried |
| `-h`, `--help` | usage |

With `--auth` on, create the owner first (`pabrik create-admin --email
you@example.com --password …`), sign in, and the console answers 401/403 to
anyone else.

Point it at the database pabrik itself uses and it is the same console. Point
it at a new file and it creates the `users` and `auth_sessions` tables that
the console needs; start pabrik on that database afterwards and its
migrations fill in the rest.

`zig build test` in that folder runs the console's own 21 tests.

The folder is a Zig package of its own (`build.zig`, `build.zig.zon`), which
is why `src/http_handlers/auth_core.zig` exists: the session cookie, the token
hash and the bcrypt hash are declared as their own module, so the standalone
program can link that one file instead of all of pabrik.

## Who may use it

The console belongs to the **owner** of the installation.

| `--auth` | who the owner is |
|---|---|
| off | the operator running the installation |
| on | the account whose `users.role` is `admin` |

Every endpoint answers `401` without a usable session and `403` for a session
that is not an owner. The page itself is served without a session: it has to
load before it can ask who is asking.

## The endpoints

| method | path | what it does |
|---|---|---|
| `GET` | `/api/admin/overview` | the counts the page opens with |
| `GET` | `/api/admin/users` | every real account (the system account is not one) |
| `POST` | `/api/admin/users` | create an account |
| `PATCH` | `/api/admin/users/:id` | change the role, or switch the account off |
| `POST` | `/api/admin/users/:id/password` | reset a password |
| `GET` | `/api/admin/vms` | the workspaces in this database, read-only (see below) |

### Machines, and the manager behind them

`GET /api/admin/vms` lists every workspace with the state its machine is in.
The state, the vCPUs, the memory and the disk come from `pabrik-vmd`, which is
another process: the console talks to it over its socket. `--vmd-socket` names
one; without it the console looks where the server looks
(`$PABRIK_VMD_SOCKET`, then `$XDG_RUNTIME_DIR/pabrik-vmd.sock`, then
`/tmp/pabrik-vmd.sock`), which is where `pabrik --saas` starts its manager.

```json
{ "manager": true,
  "vms": [ { "workspace_id": "ws_…", "workspace_name": "kabelweb",
             "state": "ready", "pid": 733578, "vcpus": 2,
             "mem_mib": 1024, "disk_mib": 512, "last_error": "" } ],
  "count": 1,
  "limits": { "min_vcpus": 1, "max_vcpus": 8, "min_mem_mib": 128,
              "max_mem_mib": 16384, "mem_step_mib": 128,
              "min_disk_mib": 128, "max_disk_mib": 65536 } }
```

`manager` is the page's permission to offer a resize. With no socket, or a
socket nobody answers on, it is `false`, the list is empty and
`manager_reason` says which of the two it was; a database the console created
for itself has no `workspaces` table and that is an empty list too, not an
error.

### Creating an account

`POST /api/admin/users` with `{"email": "...", "name": "...", "role": "user"}`.

The email is required and must look like an address; the role is optional and
is one of `admin`, `user` or `bot`. Without a password the console mints a
temporary one and returns it **once**:

```json
{ "user": { "id": "user_…", "email": "…", "role": "user", … },
  "temporary_password": "k7m2pq4rx8ntvz3d" }
```

Hand it to the account holder. The server only stores its bcrypt hash.

### Resetting a password

`POST /api/admin/users/:id/password` with `{}` resets the password to a new
temporary one and returns it. Every session that account had open is closed,
so a session opened with the old password stops working.

### Resizing a workspace's machine

The **Machines** section lists every workspace with the size its machine runs
as, and each row has a **Resize** menu: vCPUs, memory, and storage in one
dialog. **This restarts that workspace**, and that is
Firecracker, not the UI: `machine-config` (vCPUs and RAM) is accepted only
before `InstanceStart`, and the disk can only be grown with the machine
stopped. So a resize is: stop that workspace's VM, apply the size, start it
again. The guest comes back in a few seconds; the processes inside it do not.

| method | path | what it does |
|---|---|---|
| `GET` | `/api/admin/vms` | every workspace's machine: state, vCPUs, memory, storage |
| `POST` | `/api/admin/vms/:workspace/resize` | stop, resize, start |

`POST` body: `{"vcpus": 2, "mem_mib": 1024, "disk_mib": 4096}`.

- **vCPUs** `1..8`.
- **Memory** `128..16384` MiB **in 128 MiB steps**: Firecracker refuses
  anything off that grid at boot, so the console refuses it first.
- **Storage** `disk_mib` `128..65536`, and **it only grows**: a filesystem
  cannot give blocks back, so a smaller number is refused with
  `disk_mib must be larger than the disk already is`. Omit it (or send `0`) to
  leave the disk alone.

The answer is the state the machine came back in (`ready`, or `failed` with
the guest's reason) plus the sizes it now runs with. With no manager socket the
endpoint answers `503` with the same reason the list carries, and the page
never offers a control that cannot work.

Memory and vCPUs live beside the VM: `pabrik-vmd` records them per workspace
in `<root>/workspaces/<id>/vm.spec`, so the manager needs no database and a
workspace with no record keeps the manager's defaults.

**Storage needs nothing recorded**: the workspace's disk *is* the image at
`<root>/workspaces/<id>/disk.ext4`, so its size is the record. Growing it is a
`truncate` plus `resize2fs`, and **e2fsprogs must be on the host**: a guest
that was stopped rather than shut down leaves `needs_recovery` on its
filesystem, which `resize2fs` refuses, so the manager runs `e2fsck -f -y`
first. A host without e2fsprogs answers `ResizeToolMissing` instead of
pretending to grow.

The same resize is a command, which is how CI proves both sizes on a real
guest:

```bash
pabrik-vmd resize --socket /run/user/$UID/pabrik-vmd.sock \
  --workspace-id ws_123 --vcpus 2 --mem 1024 --disk 4096
scripts/vmd-resize-smoke.sh   # boots, resizes, and reads nproc, MemTotal and df INSIDE the VM
```

### The last owner

An installation with no owner cannot be administered again, so the console
refuses to demote or switch off the last active owner (`409`). Make a second
owner first.

## The database

`users` (Migration 077) already carries `role`, `is_active`, `email` and
`password_hash`. The console needs no migration of its own.

## The design gate

The console is an app screen, so the landing-page pipeline (the direction
draw, the imagery hunt) does not apply. The house rules and the measurable
laws do, and both scanners were run against the live console.

```bash
node <taste-skill>/scripts/lint.mjs src/apps/admin/index.html \
  src/apps/admin/admin.src.css src/apps/admin/admin.js
CHROME_PATH=~/.cache/ms-playwright/chromium-1248/chrome-linux64/chrome \
  node <taste-skill>/scripts/inspect.mjs "http://127.0.0.1:8083/admin#accounts" \
  --allow few-pictures,still-page
```

| view | reading |
|---|---|
| `lint.mjs` | 0 FAIL, 0 WARN |
| `inspect.mjs` `#accounts` @1440/768/390 | 0 FAIL, 1 WARN |
| `inspect.mjs` `#machines` @1440/768/390 | 0 FAIL, 1 WARN |
| `inspect.mjs` @390 alone | 0 FAIL, 0 WARN |

What the inspector measured: one typeface (system-ui), body 16px / 1.63, the
title at 30px on one line at every width, 77 words on the section, no console
errors, no sideways scroll.

Two rules are allowed by name, and this is the whole reason:

- **few-pictures** — the rule wants four picture-sized fragments on a page
  that scrolls. A sectioned console renders one section at a time, so it has
  two (`console-nav`, the open section) and cannot have four without showing
  the sections the navigation exists to hide.
- **still-page** — the motion floor of 16 elements is a landing-page figure.
  The console moves seven things, once: the masthead, the rail, the section and
  its rows, over 260ms, and `prefers-reduced-motion` drops all of it. Nothing
  loops, because a console that keeps moving is a console nobody can read.

Kept as a documented warning: **no-footage**. Also absent with its reason:
`no-real-pictures` (a console has no subject's world to photograph; its
pictures are the interface fragments it is made of).

Three lines keep a flagged pattern on purpose, each marked
`taste-skill-ignore` where it sits: the dialog's shadow (a dialog is what
floats), the table rows' bottom rule (real table rows), and nothing else.
