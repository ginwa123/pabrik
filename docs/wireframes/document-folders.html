Four states, and what each one promises

These are the only new interactions in the sidebar. Everything else (select a document, the violet active bar, the truncated title, drag to reorder) stays exactly as it ships.

state 01

Make a folder without a dialog

The section + opens a two-item menu: New document, New folder. The row appears where it will live with the name selected, so the next keystroke is the name. Enter commits, Escape removes the row and nothing was written. A subfolder starts from the folder row's own menu, so the parent is never a field you can get wrong.

The write path, in order

Every move is optimistic and revalidated. The list is read once as a whole tree, so a move is a local splice plus one write, and nothing here adds a round trip to the sidebar's first paint.

1
Drop lands. The row splices into its new list and takes the new indent.
One frame. The tree is already in memory, so no request is needed to redraw.
2
The move is written: PATCH …/documents/:id with {folder_id}, or PATCH …/document-folders/:id with {parent_id}.
Reparent and reorder are separate calls on purpose: a move between folders and a reorder inside one have different invariants, and one endpoint doing both cannot reject either cleanly.
3
The row is written through to IndexedDB in its new place.
A cold boot paints from cache before the network answers. A move that only exists on the server pops back under the old parent for one frame.
4
Revalidation replaces the tree with the server's answer.
A rejected move (409 on a cycle, a 404 on a folder deleted in another window) reverts the splice and prints the reason under the header. Never a silent loss, never a stuck ghost row.
5
The open document keeps its place: the breadcrumb re-renders, the body does not reload.
The editor is keyed by document id, not by path, so moving the document you are reading does not remount the editor or lose a draft.

Schema and endpoints

One new table, one new nullable column, one extra array on the list response. The tree is shallow by construction: a folder points at one parent, a document points at one folder.

Schema. Column names follow the existing migrations 98 and 122.
tablecolumnwhy
document_folders id, workspace_id, name, position Same shape as documents: a text id, a workspace scope, a title, and an order inside its level.
document_folders parent_id nullable NULL is the root, so "top level" needs no sentinel row. Indexed with position so one level is one ordered read.
documents folder_id nullable, ON DELETE SET NULL A document belongs to at most one folder. If a folder row ever disappears out of band the document falls to the root instead of vanishing.
document_folders created_at, updated_at Matches every other table, and lets a future "recently changed" sort exist without a migration.
Endpoints. Existing routes keep their shape; only the list read and the document patch grow.
methodpathbody / result
GET /api/workspaces/:ws/documents Result grows to {documents: [… folder_id], folders: [{id, parent_id, name, position}]}. One read for the whole tree.
POST /api/workspaces/:ws/document-folders {name, parent_id} → {folder}. parent_id null creates at the root.
PATCH /api/workspaces/:ws/document-folders/:id {name?, parent_id?, position?}. 409 on a cycle or a sixth level, with the reason in the body.
DELETE /api/workspaces/:ws/document-folders/:id Reparents child folders and documents to the removed folder's parent in one transaction, returns {reparented_documents}.
POST /api/workspaces/:ws/documents Body gains optional folder_id, so "new document here" creates it in place.
PATCH /api/workspaces/:ws/documents/:id Body gains optional folder_id. Explicit null moves the document to the root. Absent leaves it alone.
POST /api/workspaces/:ws/documents/reorder Body becomes {folder_id: string|null, ordered_ids: []}. Sibling order is per level, so the caller must say which level it is renumbering.

Decisions worth arguing about now

Each of these changes the schema or the feel of the feature. Cheaper to settle here than after the migration is written.

D1
A folder holds one parent and a document lives in one place. No multi-parent tags. "Also in" reads well in a spec and ruins every move, delete and count downstream, because the answer to "where does this live" stops being single.
D2
Folders sort before documents at every level. Two ordering spaces (folder.position, document.position) instead of one shared one. The cost is that a document cannot be dropped between two folders; the gain is that a reorder never has to renumber two tables.
D3
Deleting a folder keeps its documents. Children move up one level. The alternative, cascade delete, turns one mis-click on a folder into 31 lost documents, and there is no undo in the sidebar.
D4
Five levels, enforced on the server. The rail is 240px and --sb-mark is 16px, so level five already gives up 80px of the 216px of usable text width. The client checks first so the refusal is instant, the server checks again because the client is not the only writer.
D5
One list read returns the whole tree. GET …/documents gains folders[]. A per-folder fetch would put an N+1 in the sidebar's first paint, which is the one path the cache-first store exists to protect.
D6
The agent sees the folder path, and gets no new tool. The documents tool payload gains a path string (Split bill / POST split-bill), so an agent can group and report on the same structure a human sees. New tools are new surface area for no new capability.
D7
Keyboard and menu parity, not drag-only. Every move a drag can make is also in the row menu as "Move to…". Drag is the fast path; the menu is the one that works without a pointer and is the only path a test can drive deterministically.

Out of scope for this change

folder permissions or sharing tags and multi-parent documents folder icons and colours moving documents between workspaces a change to the document editor beyond the breadcrumb search across folders (the existing search keeps its rank)

What to approve before implementation

  1. D1 and D2: one parent per document, folders before documents. These decide the schema.
  2. D3: delete reparents instead of cascading. This decides what a mis-click costs.
  3. D5: the list read returns the whole tree. This decides the first-paint cost.
  4. The five-level cap. Five is a guess from the 240px rail; say six and it is one constant.
  5. Drag-and-drop as the primary gesture, with the menu as parity. If the menu should be primary, the drop targets change.
