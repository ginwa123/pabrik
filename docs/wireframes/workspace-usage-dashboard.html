DeepSeek and MiniMax answer with prompt_cache_hit_tokens and prompt_tokens_details.cached_tokens; neither is read, so the counters die in the parser and the row stores 0.

Not on this page, and why

Cost in dollars

The row records the model and not the provider, and a bare model id resolves to as many as 27 catalogue rows with different prices: deepseek-v4.1-flash alone. Any price join picks one at random and the figure is wrong by a factor. The only correct source is cost_usd computed at write time, where the profile that actually made the call is known, with cache reads priced at about a tenth of a cache miss.

Cache writes

cache_creation_input_tokens is 0 in all 570,865 rows. Either nothing used here reports writes or the parser drops them. It stays off the page until one row proves the number is real; a tile that is always 0 teaches the reader to ignore it.

Rates above 100%

Three rows report a cache read larger than their own prompt, all from the opencode path: 114,048 cached tokens on a 17,932-token prompt. The rate is clamped in the query and those rows are excluded from every number above, with a count shown when they exist. A usage page that can print 636% has no floor.

Server latency

/api/metrics/summary is an in-process registry that resets on restart. It answers a question about the server, not about a workspace, so it belongs on a server page and not here.

The four aggregates, workspace-scoped through sessions:

SELECT COUNT(*), COALESCE(SUM(h.prompt_tokens),0), COALESCE(SUM(h.completion_tokens),0),
       COALESCE(SUM(h.cache_read_input_tokens),0),
       COALESCE(SUM(CASE WHEN h.cache_read_input_tokens > 0
                          OR h.cache_creation_input_tokens > 0 THEN 1 ELSE 0 END),0),
       COUNT(DISTINCT h.session_id)
FROM llm_history h JOIN sessions s ON s.id = h.session_id
WHERE s.workspace_id = ?1 AND h.prompt_tokens > 0 AND h.created_at_nano > ?2;

SELECT substr(h.created_iso,1,10) AS day, COUNT(*), SUM(h.prompt_tokens),
       SUM(h.cache_read_input_tokens)
FROM llm_history h JOIN sessions s ON s.id = h.session_id
WHERE s.workspace_id = ?1 AND h.prompt_tokens > 0 AND h.created_at_nano > ?2
GROUP BY day ORDER BY day;

SELECT h.model, COUNT(*), SUM(h.prompt_tokens),
       SUM(CASE WHEN h.cache_read_input_tokens > 0
                 OR h.cache_creation_input_tokens > 0 THEN 1 ELSE 0 END)
FROM llm_history h JOIN sessions s ON s.id = h.session_id
WHERE s.workspace_id = ?1 AND h.prompt_tokens > 0 AND h.created_at_nano > ?2
GROUP BY h.model ORDER BY SUM(h.prompt_tokens) DESC;

Every column is wrapped in COALESCE: this backend reads a SQL NULL as an empty slice, which is indistinguishable from the string "". The same rule the shipped session handler follows.

Cost of the read, measured on this machine against the live 570,865-row table: 306 ms for the five queries over 43,665 rows in range. Workspace scoping starts from sessions and rides idx_llm_history_session_created, which is why it is fast. The all-workspace variant of the same question takes 3.1 s because it scans by date; if a user-level dashboard is ever wanted it needs a daily rollup, not an index.

Five decisions before code

  1. A section of its own, or the top half of Overview? This wireframe takes the section, because Overview is three fields and a chart inside it would be the only thing in it.
  2. Default range. 30 days here. 7 days has too few sessions to say anything; 90 days crosses a provider change.
  3. Does the per-call chart live here or only in the session drawer? Here it is the argument of the page. The drawer already has a handler to call: GET /api/session/:session_id/usage shipped in #938 and nothing in the app calls it yet.
  4. Fix the chat-completions cache mapping first? If yes, this page has real numbers on day one for three of its four providers. If no, the page ships honest and empty, and the fix lands later with no retroactive data either way.
  5. Cost or no cost? No cost tile until cost_usd is written on the row.
