A Compact View for chat tool calls

Today every tool call in the chat is a card of its own, so a turn that ran eight tools pushes the agent's answer off the screen. This keeps the Dev View exactly as it is and adds a second rendering, Compact, that folds a run of calls into one card, with a setting in Settings → User → General to choose between the two.

Wireframe only. Nothing is implemented yet, and the Dev View is not proposed for removal. The two chat panes below are sketches drawn from the current components, not screenshots.

The setting

It goes in the Interface block of the General tab, beside Browser-style tabs. That block is already the home of app-local interface preferences, which is exactly what this is: a preference about how the app looks, not about how the agent runs.

Settings

User — applies everywhere

General

Interface
Browser-style tabs Keep several chats, boards and pages open at once in a tab strip above the content area. Off restores the single-view layout.
Chat view How tool calls are drawn in the chat. Compact folds a run of calls into a single line and keeps a failed call in view. Dev keeps today's full card for every call.

The two states of the control are the same row with the other option pressed. The choice is remembered per user, the way Browser-style tabs is, and it takes effect in every chat that is open, with no restart.

The button called Compact in that toolbar is a different thing entirely: it compacts the conversation history. That is why the setting in General is called "Chat view", and why its two options are "Compact" and "Dev".

What a card shows

The compact view does not invent a summary: the card behind the group is today's card, and it already carries the one argument you would want to recognise the call by, plus how it ended. The rule is per tool, so a card reads as the tool's own subject rather than a JSON dump.

The rules that keep it safe

  1. The cards are the dev cards. Unfolding the group card shows the same cards the dev view shows, one per call. There is no second visual language to learn, and the full detail is one click away.
  2. A failure stays inside the run. The failed call keeps its place in the group, marked in red, and the group card says how many calls failed, so a folded group never hides that something went wrong.
  3. A question waiting on you opens the group. ask_user is the one call the human has to act on, so a group that holds one starts open rather than folded.
  4. A running call is counted too. The group card counts the calls still running, so a long call never looks like a call that never happened.
  5. Nothing changes for the model. The setting decides what the chat draws. The history, the compaction and the request that goes to the provider are untouched.
  6. One place decides. The mode is chosen in Settings → User → General and nowhere else. There is no toolbar switch, so no two places can disagree.

Open questions

Two of these are already answered. A failed call keeps its place inside the run, and the group card says how many failed; it is not lifted out of the group. And there is no toolbar switch: the mode is chosen in Settings → User → General and nowhere else.

  • Where the preference is stored. The proposal is app-local, in the browser storage of the app, the same place Browser-style tabs lives, because it is a preference about the interface and not about the agent. The alternative is config.json, which would travel with the profile and let a workspace override it. Which one do you want?
  • The name. Compact already means conversation compaction in the composer toolbar. The two view modes are named Compact view and Dev view, and the toolbar control says View: Compact. Is that clear enough, or should the modes be named something else, such as Simple and Full?
  • Does Compact fold the agent's prose too? The proposal says no. Only tool calls change; the agent's own sentences are left alone.
  • What happens to a run of one call? The proposal leaves a lone call as a single line, with no group row to unfold.

What the gate said

lint.mjs, the source scanner: 0 FAIL, 0 WARN. The monospace rule is satisfied by making every tool name, path and command a real code element, which is what they are.

inspect.mjs, the real browser at 1440, 768 and 390: 0 FAIL, 2 WARN. The hero headline is 7 words and 2 lines at every width, the body text is 17px, and there are two typefaces: the app's text face and the app's mono, the mono only on code.

The two WARNs, defended. no-real-pictures and no-footage: this is a wireframe for a chat interface, and the honest picture of the subject is the interface itself. The four data-ui fragments are the settings panel, the two chat panes and the composer, and each is a live mock rather than a picture of a mock. There is no clip here that a video would honestly show.
