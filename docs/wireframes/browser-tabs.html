Every session is a tab

Try the seven states Wireframe and plan, no code yet · desktop /app · 5 November 2026 · task_1793890522320_3

A chat session already outlives the window: it runs on the server, it survives a reload, and the sidebar lists it. What it has no equivalent of is the browser tab: one named pane that stays open, stays in the same position, and says on its face whether the run inside it is working, waiting for you, or dead. This is the wireframe for putting that back, over a tab engine that never left.

Today: one surface, no tabs

The app shows exactly one thing at a time. Opening a second session replaces the first, and the only way back is the sidebar list, which is also the only place that knows a run is waiting for you. The screenshot below is the current chrome: a 288px rail, a 44px app bar carrying the session name, the transcript, the composer.

What that pair really removed is one component and its spec. The engine stayed, tested and wired.

Why the last strip was confusing

Three causes, all readable in the deleted code, and two of them are no longer true, because the things the strip needed were built after it was removed.

It was a second list
The old TabBar rendered a glyph, a truncated label and a close button: the same three facts the sidebar row 288px to the left already carried. Two lists of the same sessions, scrolling independently, with no rule about which one you were supposed to use.
It carried no state
Nothing on the tab said the run was working, finished, or failed. The vocabulary for that landed a month later: status dots on the sidebar rows in d9ea13c20 (#949, 14 October), the elapsed/activity chip in 04c87ca14 (#861, 9 October), the local-first session list in 8d33057f0 (24 September). The strip was deleted before there was anything worth painting on it.
It was invisible and unproven
Default off, so nobody met it. Turned on, the whole layout changed at once, including for kanban boards and design canvases whose tab identity follows rules a user cannot see (taskChatRendersInItemTab: a design chat is a dialog inside the canvas tab, a kanban chat is its own tab).

Proposal: a tab is a session

One persistent tab per session, and the tab carries the run. Seven tabs below: one home (the chats list), four chat sessions, two workspace items. The session that needs you is not the active one, which is the whole point of the row.

Persistence, in order

“Persistent tab” is not a new promise. It is the promise the session already keeps, made visible. The strip restores in five steps, four of them local, and the network only ever corrects what the window already painted.

1
The window reads its own tab list from localStorage: pabrik-tabs:<windowId>, version 1.
Already implemented: parseTabList returns tabs, the active id and the closed stack, and repairs a bad payload to a fresh list instead of throwing. Per-window, not per-account: two browser windows keep two different open sets.
2
Labels come from the local session cache in IndexedDB, before any request returns.
SessionEngineDb.primeFromCache already holds every session row the sidebar has ever seen, with the server's own name. A cold boot paints seven real names instead of seven “Chat”.
3
The live feed fills the dots: workers SSE says which sessions are running, then re-syncs on every reconnect.
App.vue already owns this map and re-reads it from the DB when the bus reopens, so a laptop that slept for an hour paints the truth, not the state it left.
4
One session-list read reconciles the rest: names, review flags, and which tabs are gone.
The same call the sidebar makes. A tab whose session is absent becomes the gone state rather than disappearing silently: a tab vanishing on reload reads as a bug, and silently dropping the user's place is worse.
5
The URL is applied last: ?tab= names the tab, whose own target names the session.
A reload, a deep link and a back button all land on the same tab, because the tab was never the source of truth; the target was.

What it takes to be real

No new endpoint, no new table, no backend change in P1. The engine, the URL contract, the keyboard map and the per-session live state all ship today; what is missing is a component, two store behaviours, and one small runtime map that turns three existing sources into a dot.

P1: the strip returns visible, no new state
New AppTabStrip.vue mounted as one element inside <main>; tabs from tabsStore.tabs, activation and closing through the existing store actions and applyActiveTabToUrl. Right-click menu (close / close others / close to the right / open in a new window), middle-click close, wheel scroll, drag reorder, the ▾ overflow list, the one-tab 0px rule. Default flips to on; the Settings switch stays as the escape hatch with honest copy.
P2: the dot the reason it exists
stores/sessionRuntime.ts: sessionId → running / needsYou / failed, merged from processingState, workerActivity, agentError, and the session rows (cache first, one list revalidate on session.updated). The sidebar row gains an “open in this window” mark so the two lists stop being strangers. Optional P2.5: put needs_human_review and last_finish_reason on the SessionEvent so the dot updates without a list refresh: two fields the backend already has on the row.
P3: restore, rename, gone the persistence half
restoreTitlesFromCache() on boot; the gone state after the first session-list answer; a session renamed while the window was closed re-labels itself from the list instead of keeping a stale title. The app bar drops its title when tab mode is on (the strip already says it), so the chrome total stays 80px, and the 44px row keeps its controls.
P4: adopt, and clean up needs the human's answer
On first enable, offer to adopt the last 10 sessions that are waiting for review or were touched in the last 7 days; otherwise start with one home tab and adopt on open. Then delete this wireframe, as the other wireframes are deleted when they ship.

Not on this page, and why

A full-width strip above the sidebar

Browser-true, and wrong here: the rail's 48px header carries the workspace switcher, which is the app's identity and must stay at the window's top-left corner. The strip also has to sit under the scroll and overlay behaviour of <main>, not above it, so it cannot become window chrome. Cost of the compromise: the strip starts at x = 288, not x = 0.

Every session in the list, opened as a tab

The list pages 20 at a time and a workspace has hundreds. Opening them all is 50 tabs (MAX_TABS) of noise and an unreadable row. A tab is created the first time a session is opened and then persists until closed. The tab set is a place, not a mirror of the database.

Deleting the sidebar list now that tabs exist

The list is the inventory: search, pins, rename, delete, projects, documents. The strip is the open set. Two surfaces, two jobs. The failure of the old strip was that it did neither job better than the list.

Closing a tab deletes the session

No. Closing is forgetting a pointer, the same way closing a browser tab does not delete the page. Deleting stays where it is, in the list's context menu, behind a confirm.

Syncing the tab set to the server

Tempting and premature. The set is window state, and the app already scopes it per window id; a server copy brings conflict resolution between two windows, a migration, and a second source of truth for something a reload rebuilds in 40ms from local storage.

Tab groups, pinning, a drag-out new window

Three browser features that each need their own decisions about persistence and identity. The closed stack (10) plus the overflow list cover the real need (getting back to a session you closed) without any of that.

Decisions, and the two I need from you

  • A tab is a session. One tab per session id, created on first open, restored on every boot, closed only when you close it. Renaming the session renames the tab; it never creates a second one. decided
  • The dot is the feature. If the strip only named sessions it would be the sidebar again. The reason to spend 36px is that four sessions can be in four states and the row tells you which one wants a human without being opened. decided
  • One row, no second panel. The strip lives inside <main>, above the app bar, and costs 36px. It does not touch the rail's geometry or its scroll. decided
  • Strip on by default, and 0px when there is one tab. The old default-off is what made the feature die; the 0px rule is what makes default-on safe. decided
  • Adopt or start empty on first enable? My default: offer to adopt the last 10 sessions that are waiting for review or were touched in the last 7 days, once, with a button, so a returning user sees their work, and a new one sees nothing. needs your answer
  • Should the app bar keep the session title? My default: drop it in P3 and let the tab own the name. The alternative is the two-name layout in the proposal frame above, which is honest but redundant. needs your answer
