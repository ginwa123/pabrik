4Traps found while measuring — read before implementing

① The pill rail is already handled — for rows only, and asymmetrically. .has-pill-rail puts padding-right: 48px on every row (ChatView.vue:5462-5471) so the rail's pills (18 px + 32 px rail) cannot sit on a bubble. Today that 48 px hides inside the empty gutter. Full-bleed makes it a visible 48 px right / 16 px left asymmetry in any chat with ≥ 2 user messages — the mirrored-padding fix belongs in the same change.
② The composer dock is not covered by that rail gutter. Site 4 has no has-pill-rail rule, so full-bleed moves the input card's right edge into the rail's band. Check it with the rail visible before shipping.
③ The tool cards already follow the row. .tool-sequence, .tool-item and .chat-tool-card are all width: 100% with min-width: 0, and .chat-tool-card pre { overflow-x: auto } — so wide payloads scroll inside rather than stretch the card. No change needed, and ChatView.tool-width.spec.ts pins all of it, including the exact class="min-w-0 flex-1 w-full" container.
④ The floating composer is vertical only. --chat-composer-inset / .last-transcript-row (ChatView.vue:5564) pad the last row down, so a horizontal change cannot desync them. VirtualScroller's measureItems() reads offsetHeight, so horizontal width is invisible to the height model too — no scroll anchoring risk.
⑤ No test pins the cap. Grepping max-w-4xl across src/, tests/ and tests/functional_ui/ finds the four sites in ChatView.vue and nothing else (the other hits are the compiled bundle in webapp_assets.zig). The blast radius is the four sites.

5Open questions — pick one per line

  1. Which option — A plain full-bleed, B full-bleed with a 24 px inset, or C a width token + control? C, defaulting to full — it does exactly what you drew and can be dialled back to 896 without another PR.
  2. If C: where does the control live — chat app bar, or Settings → Appearance? app bar; you are looking at the chat when the gap annoys you.
  3. Should prose alone keep a reading measure (~90 ch) while cards and diffs go full width? no for now — it re-creates a gap around paragraphs, which is the thing you drew.
  4. Does the sidebar count? With the sidebar open the column is 1162 px, so the change is worth only 266 px; with it hidden it is 554 px. the cap is per-column, so both are fixed by the same change — nothing extra to do.
  5. The composer: follow the transcript, or stay at 896 like a document's signature block? follow it — a wide transcript over a narrow input card reads as a bug.
  6. Add tests/functional_ui/chatview_width_test.py asserting gutter 0 at 1450 px, so the cap cannot creep back? yes, one assertion per option chosen.
