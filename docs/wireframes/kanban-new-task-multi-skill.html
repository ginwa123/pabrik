Pick several skills for one task

This is the design record for PR #966. The card asked to let a task carry several skills (today it carries one, PR #958) and to see the wireframe first. Round 1 was this wireframe; you then chose V1 with a search field, and the implementation landed on the same branch: DB, backend, dialog, tests. The panes below are live, and section 8 records the decisions.

The defect to absorb: the directive is baked twice

The frontend and the backend both append #Skill <name> to the same message on create_and_run, so the agent receives it twice. This card's own note is the live specimen: it ends with the same line repeated.

Frontend bake
buildTaskCreateMessage.ts:26-29 
lines.push('', `#Skill ${skill}`)
 Backend bake
kanban_tasks_create.zig:225-227 
"{s}\n\n#Skill {s}", .{ base, skill }

Both run for create_and_run, so the message reads ...\n\n#Skill x\n\n#Skill x. With N skills and no fix, N becomes 2N. The proposal below gives the note exactly one owner, the backend, because that is the API-level guarantee, and one line per skill.

6Wire and DB shape (the method, layer by layer)

The set is stored the way this repo already stores its other per-task lists, and the column is renamed rather than duplicated: one source of truth, no backfill step, no data loss.

LayerTodayProposed
DB workspace_item_tasks.skill_name TEXT NOT NULL DEFAULT '' workspace_item_tasks.skill_names, same type and default, holding ||-joined names. Migration 112 is ALTER TABLE ... RENAME COLUMN skill_name TO skill_names. A single name is a one-element list, so existing rows are already correct, and the column keeps its position, which matters because the listers map row.values[N].
Wire skill_name: string skill_names: string[], a real JSON array like Migration 111's depends_on ("a real JSON array, unlike tags"). The legacy skill_name: string is still accepted as a one-element list.
Why not a join table Migration 111 gave dependencies the edge table kanban_task_dependencies because the board queries them: what blocks this card, and the move gate. Nothing queries by skill, and image_urls and video_urls already set the precedent for a ||-joined list column. I will switch to the join table for symmetry with dependencies if you prefer, and the change stays in one place.
Note The frontend bakes it and the backend bakes it, so 1 skill produces 2 lines. Backend only, one #Skill <name> line per skill in pick order, appended after the existing body. The frontend stops baking, which is what turns today's duplicate into a single complete directive list.

8Decisions

Q1. Picker: V1 with a search field, chosen A checkbox dropdown that stays open, a search box that narrows the rows by name or by description, and removable chips under the row. Shipped in this PR.
Q2. Cap: 20 skills per task, accepted A 21st skill is a 400 with "skill_names: at most 20 skills per task", so neither the row nor the agent's first message can grow without bound.
Q3. The legacy single skill_name field, kept Accepted as a one-element list whenever no array is sent, so curl scripts, older desktop builds and any other client keep working.
Q4. Storage: the skill_names list column, accepted Migration 112 renames the column. Surfacing a task's skills on the card or in the detail view stays out of scope: the wire already carries them and no component draws them, which is worth its own card.

9Design pass, and what the meter said

The skills in play here are the repo's wireframe-measurement skill (assert DOM geometry in agent-browser, never trust a screenshot) and design-taste-frontend. The taste skill's own scope note excludes app surfaces, so I used its component case, which is exactly this document: skip the direction draw, match the surrounding design, apply the house rules and the laws, then run the gate.

House ruleHow the picker proposal answers it
Two or three sizes do the work The picker uses two: the 13px pill label and the 12px chip and count. No third size, no in-between.
One ground, one ink, one accent The accent is the violet tint, used for the selected checkbox, the count badge and the chips. The "Clear all" action is the one blue link in the dropdown.
Flat controls, no gradients, no glow Pills, rows and chips are flat fills. No gradient inside the picker, and nothing inside it lifts off the page. The mock windows and their dropdowns are the only two surfaces in this document that do, which is the place the rule allows it.
Surfaces separated by a tone step, not a line Proposed rows separate by a tone step and space. The tick is drawn as an SVG in the proposed panes rather than the literal text glyph the shipped component uses, since a glyph tick is the device the house rules replace. Pane A keeps the shipped look and says so.
Statements are paragraphs Every explanation here is running text at 16px with a measure capped near 68 characters. Nothing is set large to look like a headline.
Where the surrounding design wins The pills keep a 1px border and the tables keep their row lines, because the pabrik dialog and the repo's wireframe tables already look like that, and this component is not a page that gets to re-decide the app's language. The mock windows and their dropdowns carry data-ui, which is the skill's own marker for a cropped interface fragment that keeps its true sizes and its own lines.

The gate reading

lint.mjs and inspect.mjs both ran against this file. The first pass found 26 lint FAILs and 11 inspector FAILs, and the fixes are in this revision: body copy moved from 12px to 16px (187 text blocks were under 13px), the 17 uppercase letter-spaced labels became sentence case, the em-dash habit is down to one, tracked text glyphs became SVG, the document's own borders became tone steps, and paragraph measures were capped. The measurements that remain are the mock interface fragments, which the skill exempts on purpose.

Two readings I will not fake, and you should know about both. No motion layer: the inspector fails a page with fewer than eight moving elements, and this is a spec document, so adding entrance animations to satisfy the meter would fake the very thing the document is about. No photographs: the imagery floor is for a public page. Here the pictures are the four interface fragments, which the skill counts for software. Everything the inspector measures about the picker itself is real and measured.
