What it takes to be real

One route, one transaction, no new table. The route belongs beside the other session routes in src/http_routes.zig, and the handler reuses llm_history.delete_session rather than re-implementing the delete.

DELETE /api/llm/session/:session_id

200  { "deleted": { "llm_history": 105, "sessions": 1, "worker": 1, "task": 1 } }
404  { "error": "session not found" }
500  { "error": "delete failed", "detail": "..." }

The response carries the counts it actually removed, so the strip in the chat pane can print a number the server confirmed instead of the number the dialog guessed.

Fifteen tables carry a session_id column. Deleting only sessions leaves every one of them behind, and the next GET /api/llm/session still returns nothing while 18,001 orphaned llm_history rows keep the table at 606,683. The cascade is one transaction:

BEGIN IMMEDIATE;
DELETE FROM worker                     WHERE session_id = ?1;
DELETE FROM session_queue_messages     WHERE session_id = ?1;
DELETE FROM session_pending_question   WHERE session_id = ?1;
DELETE FROM session_background_process WHERE session_id = ?1;
DELETE FROM session_progressive_tool   WHERE session_id = ?1;
DELETE FROM session_skills             WHERE session_id = ?1;
DELETE FROM session_skill_events       WHERE session_id = ?1;
DELETE FROM session_agents             WHERE session_id = ?1;
DELETE FROM session_group_members      WHERE session_id = ?1;
DELETE FROM session_activity           WHERE session_id = ?1;
DELETE FROM session_plan               WHERE session_id = ?1;
DELETE FROM skill_eval_results         WHERE session_id = ?1;
DELETE FROM skill_eval_runs            WHERE session_id = ?1;
DELETE FROM logs                       WHERE session_id = ?1;
DELETE FROM llm_history                WHERE session_id = ?1;
DELETE FROM kanban                     WHERE workspace_item_task_id = ?1;
DELETE FROM workspace_item_tasks       WHERE id = ?1;
DELETE FROM sessions                   WHERE id = ?1;
COMMIT;

messages_fts needs no statement of its own. It is an external-content FTS5 table over llm_history, and the llm_history_ad trigger already removes the index entry on every row delete. Adding a manual INSERT INTO messages_fts(messages_fts) VALUES('delete', ...) would double-delete and corrupt the index.

What the code already has, and what it does not

  1. The UI half exists and is unreachable. ChatsList.vue:666 has a complete removeChat(): it splices the row, evicts the cache entry, clears the active chat, and calls the API. Nothing in the template binds it. It is exported through defineExpose and called only by a unit test.
  2. The API call points at a route that does not exist. api/chatHistory.ts:265 sends DELETE /chats/:id. There is no /chats prefix anywhere in src/http_routes.zig; the session routes all live under /api/llm/session. The call 404s today.
  3. The backend half exists and is never called. llm_history.delete_session at src/agentic_loop/llm_history.zig:3846 deletes the sessions row and broadcasts the deleted SSE event that ChatsList already listens for. It has no caller and no route, and it touches one table of the fifteen.
  4. 1,476 of 3,511 sessions are also kanban cards. workspace_item_tasks.id equals sessions.id since Migration 052, so a delete that ignores the task table leaves a card on the board pointing at a chat that no longer exists.

Not on this page, and why

Undo, or a soft delete

A deleted_at column would make the action reversible, and it would reclaim nothing: the rows stay in a 606,683-row table and every read path needs a new filter. The reason to delete a conversation is that it is taking up space, so this is a hard delete and the dialog says so.

Bulk delete, or clear all

A second destructive surface with no per-row confirmation, on a list that pages 20 rows at a time and can be sorted either way. It is the fastest way to lose a conversation you did not mean to select. Single delete first, and only if it gets used.

A delete button on the kanban card

The card menu already owns a destructive action for the same row. Two delete buttons for one object is how a user deletes the wrong thing, so the card keeps its own and the chat menu is the only place a chat is deleted.

A hover cross on the row

The row is a <button> inside a virtual scroller, so a nested button is invalid markup, and a hover-only control is unreachable by keyboard and invisible on touch. The context menu is already arrow-navigable with role="menuitem".
