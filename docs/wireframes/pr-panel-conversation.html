The PR panel, redrawn

Pabrik shows a change request as a list of files and a merge button. Three things a reviewer actually needs are missing: what the request says, what was said about it, and why the merge is held. This wireframe adds those three, and it adds them without changing what the panel does.

Wireframe only, no code changed. Drawn against main at bcb41305e. Sources read: SidebarDiffPanel.vue, MergeBox.vue, helpers/mergeWording.ts, helpers/forgeWording.ts, helpers/markdown.ts. The panel is drawn at its real default width, 280px (RightSidebar.vue), inside a 320px frame.

What changed, part by part

The header. The number and the state stay. The title arrives in two lines, the author and the age under it, the base and head refs beside them. The title is truncated, never wrapped into a third line: the full text is the tooltip and the forge link.

The chips. Two, at most three. Each is a status, not a button with a label on it: 2 checks failed opens the Checks tab, 1 review requested opens the Conversation tab. They replace the “some checks were not successful” sentence, because the sentence is the reason the reviewer has to leave the app.

The list. The same sixteen rows in the same order, grouped by folder so a long list can be read, with the totals in the heading. Grouping is a display change only; the click behaviour is untouched.

The merge box. Untouched in behaviour, one line changed. The button, the method memory, the delete-branch checkbox and the confirm step all stay as they are.

§4The Conversation tab

The question this answers is the one a reviewer asks first: what was said about this, and who is holding it? On the forge that is the request body, the issue comments and the review verdicts. Here it is one tab, read only, with the review decision at the top because that is the sentence behind “Merging is blocked”.

The body above is ginwa123/pabrik#1010's real body, trimmed to what fits a 280px panel. The comment and the review are shaped like the real ones on #1003 and #983, with the content shortened.

The anatomy

The decision line. reviewDecision is APPROVED, CHANGES_REQUESTED, REVIEW_REQUIRED or empty. It is the sentence the merge box is missing: today the box says “Required approvals or checks are missing”, and this says which.

The body. The request's own description, rendered as markdown, because that is how it was written.

Comments. Issue comments, oldest first, each with its author and its age.

Reviews. A review is a comment with a verdict on it, so it is drawn the same way with the verdict attached: approved, changes requested, or commented.

Why v1 is read only

Writing a comment is a write path, and it is a different job: gh pr comment on GitHub, glab mr note create on GitLab, and the whole glab mr note family is still marked experimental. A read only tab is honest about what it is, and it is not a dead end: the footer's one action takes the reader to the place where the three things they might want to do are.

The composer and the three verdicts are drawn below in a lighter tone, labelled as the second version, and they are not part of this proposal.

The one rule that is not negotiable. A comment on a pull request can be written by anyone who can comment on the repository. helpers/markdown.ts renders markdown with marked.parse and no sanitiser, and the repository ships no DOMPurify. Every body in this tab, the request's own body included, goes through renderMarkdownHtml() or renderInlineMarkdownHtml(), and never through marked.parse directly. The test is that <img src=x onerror=…> arrives in the DOM as text.

§5The tab strip, measured

A sixth tab does not fit. The numbers below are measured in the browser, on the two strips drawn in this page, at the app's own metrics: 12px labels, 10px of padding a side, a 4px gap. The cluster of labels is what the 280px panel has left after its padding and the refresh button: 238px. The table is the page's own measurement, so it moves if the drawing does.

StripLabels needStrip hasHidden at 280px
Today: Files, PR, Commits, Checks, Evals – – –, which is why Evals cannot be reached
Proposed: Conversation, Local, Changed, Commits, Checks, Evals – – –, so the strip must scroll

So the strip needs an affordance, and it needs one today, before the sixth tab arrives. Four things, all small:

  • Two chevrons that float over the cluster's right edge, shown only when the strip overflows, and they cost no width of their own. They do cover the last 46px of the cluster, so about 192px of label is readable at a time.
  • The active tab is scrolled into view whenever it changes, so Conversation is never the tab you cannot see.
  • Left and right arrow keys move between tabs. The strip already carries role="tablist", so the keys belong to it.
  • ?tab=conversation opens the tab directly, and the tab survives a panel reload.

A fade on the right edge is optional and is not drawn here: the chevrons and the half visible label carry the same message, and a fade is decoration on top of a control.

Today the verdict is a sentence about a category. The same two facts, as chips, are countable, clickable, and each one knows where its detail lives.

Both sentences come from helpers/mergeWording.ts, which already knows the state. The chips need one thing the box does not have yet: the count of failing checks and the review decision, which is the same read the Conversation tab makes.

§8Decisions, each with a recommendation

#QuestionRecommendationAlternative
D1 Sixth tab, or a section inside the request tab? Sixth tab, first in the strip, the order GitHub uses, with the strip fix shipped in the same change A section inside the request tab would sit in the file list's own scroll, so only a reader who is already looking at files would ever see it
D2 Read only, or with a composer? Read only in the first version, with one action: open on the forge Writing is a second card, and on GitLab the command family is still experimental
D3 The forge's conversation, or the agent's session? The forge's conversation The agent's session is already readable in the peek panel, and a request tab showing the agent's chat would not answer “who is stopping me”
D4 What do the two file tabs say? Local and Changed Keeping PR is shorter, but PR is the forge's noun and the tab is also on GitLab
D5 Where does the title go? The header, under the number, two lines, truncated The band is 36px tall and cannot hold a title; growing it would push the file list down
D6 Does the request tab open on the file list, or on the conversation? The file list, as today, and the conversation is one click away and deep linkable Opening on the conversation is one word of code, and this is the one decision worth revisiting after the first week of use

§9What shipped, and where it differs

The implementation landed after this document was accepted. Six places differ, and each one is a decision the code had to make that the drawing could not:

  • The two file tabs are “Local” and the forge's own “PR” / “MR”, not “Changed”. The point of the rename was to tell the working tree apart from the request's diff, and “Local” does that. “Changed” would also have taken the forge's name off the surface, and this repository's convention is that the forge names itself (helpers/forgeWording.ts).
  • The chips come from the status read, not from a second one. gh pr view already answers for the merge state, so reviewDecision and statusCheckRollup were added to that one call: the review chip and the failing-check count cost no extra spawn, and they are right on the 30-second poll instead of going stale on a tab switch.
  • The merge box's counted sentence is its headline, except when the merge is blocked. Then the headline still says “Merging is blocked” and the counts move to the line under it, because a blocked merge must say so.
  • The Conversation tab's count appears once the thread has been read. The count is the thread's size, so the tab cannot show it before the tab has been opened.
  • The read asks for less than §7 said. The field list is body,title,number,url,author,createdAt,comments,reviews,reviewDecision: latestReviews is not needed, because every review is read and the verdict comes from reviewDecision.
  • GitLab reads the notes best-effort. The GitLab CLI's JSON does not always carry them, and this machine has no GitLab token to check against, so the panel says so in the thread instead of showing an empty list that reads as “nobody commented”.

The composer and the three verdicts are still deferred: writing is a second card.

The four findings, and why each one is defended

  • still-page (FAIL, allowed). The motion budget counts elements that move while a page loads and scrolls. This document is a specification, and adding entrances to it would fake the thing the document describes. The motion belongs to the panels it draws.
  • no-real-pictures (WARN, allowed). The subject of this document is an app panel. The honest picture of a pull request panel is the panel itself, drawn at its real width of 280px from the real request, and there is no photography of one to find.
  • no-footage (WARN, allowed). The same reason. No honest clip of a pull request panel exists.
  • first-action (WARN, not allowed, defended). The first screen of a specification is its summary, which is the table in §1. A call to action on a spec page would be decoration. The one control the page owns is the toggle in §4, and it is where the reader reaches it.
