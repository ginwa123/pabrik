Agents group in one session

Four agents share one thread. The lead splits your request, an @mention hands a piece to a worker, and anything you type reaches whoever is running.

Read how a turn is routed

It is buildable, and about two thirds of it already runs. Every message row already records which agent wrote it, the loop already takes a per-turn agent override, and an interrupt already reaches a running agent at its next step.

What is missing is narrower than it looks: a session can hold exactly one agent, nothing in the schema says who a message is addressed to, and no agent may hand work to another agent. Those three are the whole job.

The turn router

The loop already runs one iteration per model call, and each iteration already does four things in order: check for a cancellation, check for an unanswered question, drain the message queue, then resolve which agent is speaking. A group thread needs no second loop. It needs the fourth step to consult a router.

  1. Drain the queue as today. A row from you arrives as a user turn, so an interrupt needs no new delivery path at all. It is read at the top of the next iteration, which means after the tool call in flight finishes, not mid-call.
  2. Read the newest row of the thread. If it carries an addressed_to mention, that agent speaks next. If it carries none, the lead speaks. If the last speaker was a worker and it mentioned nobody, the lead speaks.
  3. Set the speaking agent through the same override slot a spawned sub-agent already uses, so the system prompt, model, temperature, reasoning effort and tool set all come from that agent's stored config.
  4. Render the transcript with an author on every row. The agent must read the room, not its own private history, so each row arrives as [Security Engineerr] … and the system prompt names the author set.
  5. Write the reply with the author's name in the agent column that every row already has, plus the mentions its text produced.
  6. Count the hop. On the eighth, or on a lead reply with no mention and no open subtask, close the turn and leave the thread waiting for you.

What already runs

Every message row already records its author. llm_history.agent is a per-row text column with a default of 'Agent', added in migration 6 and written from the saving call's agent name. A shared thread with four authors needs no new column to tell them apart, only a renderer that prints the value.

The loop re-reads the speaking agent from the database on every iteration and lets a per-turn override replace it. That override is how an agent's own system prompt, model and tool set reach a turn it did not start. It is the exact seam a mention router needs, and it is already wired.

An interrupt already works. The queue is a real table, ordered by creation, and the loop drains it at the top of every iteration. What it does not have is a target: a row is addressed to the session, so it always reaches whoever happens to be running.

Parallel agents already exist too, as a fan-out of up to twenty at a time, each on its own thread with the parent's session id. That is a different topology from a room, and it is worth keeping both: the fan-out for a burst of independent research, the room when the agents have to argue.

A session has exactly one agent

This is the real blocker, and it is structural rather than incidental.

The table that remembers the current agent is keyed by session id, so a session holds one name, not a roster. The loop derives a single speaking agent per iteration from that row. Handing work sideways is refused by design: the three tools that start or fan out work are stripped from every agent that is not the main one, so a worker cannot mention another worker and have it act.

A spawned agent does not even join the room. It gets a freshly minted session id and its own history rows, so nothing it writes is visible to its siblings. Requirement one, that every message is visible to every agent, fails there by construction.

Nothing in the schema carries an address either. No mention column exists anywhere in the migration chain, and the queue row is keyed by session alone. On the client, the message type has no author field at all, and the event stream deliberately drops session events for sub-agent ids, so a group view cannot even discover the other agents from the live feed.

The tables it needs

Three additions, all of them additive. No existing row is rewritten, which is why this can land without a data migration.

CREATE TABLE IF NOT EXISTS session_group_members (
    session_id  TEXT NOT NULL,
    agent_name  TEXT NOT NULL,
    role        TEXT NOT NULL DEFAULT 'worker',
    position    INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (session_id, agent_name)
);

ALTER TABLE llm_history            ADD COLUMN addressed_to TEXT;
ALTER TABLE session_queue_messages ADD COLUMN target_agent TEXT;
ALTER TABLE sessions               ADD COLUMN group_lead   TEXT;

addressed_to holds the mention list the row produced, empty for a message that addressed nobody. target_agent is null for a message meant for whoever is running, and names an agent when you address one. group_lead on the session is what makes the router treat the thread as a room instead of a single-agent chat, and it keeps the old behaviour as the default.

What can go wrong

  1. Agents that mention each other forever. Two workers can hand the same task back and forth and burn tokens with no progress. The hop budget on the session is the stop, and the lead closing the turn is the escape.
  2. A room costs more than one session does. Every agent reads the whole thread, so a turn re-sends the text of every author. The compaction path already exists and already runs on a threshold; group threads need a lower one and a summary the whole room shares.
  3. An agent that believes it wrote the others. If the transcript is rendered as one undifferentiated assistant history, every worker will answer for work it did not do. Author stamps on every row and a system prompt that names the roster are the fix, not a nicety.
  4. Names with spaces. Three of the agents in this workspace are named with a space in them. The composer's mention matcher only takes a word character run, so it cannot see @Security Engineerr. Resolve mentions against the roster by longest match, or give each member a slug, and keep the display name for the bubble.
  5. Two agents writing at once. The session lock exists and is what an HTTP run already takes. A group thread has to take it per turn, not per session, or the second agent blocks the first one's thread for the whole run.
  6. A worker that stops caring. A mention that nobody answers leaves the thread hanging with no state. The roster needs a per-member status that is read from the run, not inferred by the UI.
