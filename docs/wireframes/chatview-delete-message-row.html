Delete one message row

One row of llm_history, not the conversation. And a toggle that shows every row raw, because the grouped transcript does not draw them all.

Every row on this page is real, from session task_1794055749259_2, read out of ~/.config/pabrik/agent.db on 7 November 2026. Wireframe only: nothing here is implemented.

Two views of the same rows

The grouped transcript is for reading. It draws a bubble per group, and a group can hold several rows, so it cannot show you which row is which. The toggle in the app bar swaps it for the raw table: one line per llm_history row, in created_at_nano order, with the role, the tool, the content, whether the row is still fed to the model, and the tail of its id.

This session is the argument for the toggle. It has 7 rows and the grouped view draws 5 of them: three assistant rows carry only tool_calls_json and an empty response_content, so the grouped view renders nothing for them. You cannot delete a row you cannot see.

Drop from context instead

Most of the time the goal is not to destroy the row, it is to stop the model reading it again. That already has a column: is_feed_to_llm, added by Migration 5, and getLLMHistories already filters on it. Setting it to 0 takes the row out of the model's context while getSessionMessagesSorted, which does not filter, keeps it in the table. Reversible, no data lost, and the row says so in the Context column.

A group is not a row

The grouped view draws one MessageGroup per scroller item, and a group holds group.messages, which can be several llm_history rows. Consecutive user messages land in one bubble. So the action button belongs to the message item, not to the bubble, or three identical rows would share one delete.

These three are real: a routine fired three times in a row in session item_1793535810996950572, and all three carry the same text. In the raw view they are three separate lines with three separate ids, which is the whole reason the toggle exists.

What it takes to be real

The view mode is not a new mechanism. ChatViewMode is already a two-value union, 'dev' | 'compact', persisted in config.json as chat_view and read back by chatViewModeFrom. 'raw' is a third value on the same union, so it travels with the profile like the other two.

The raw view is its own component, not a branch inside ChatView.vue. ChatView keeps the composer, the scroll state and the session reads; it only chooses which of two children to mount. RawHistoryView.vue owns the table, the row menu, the inline confirm and the undo strip, and takes the rows ChatView already has. Nothing about grouping, bubbles or the VirtualScroller leaks into it, and nothing about table columns leaks back.

The toggle sits in the app bar's right cluster, beside the transcript-width control and the close button, and it gets there the way the width control did: a composable, not a prop. ChatAppBar.vue's own header says the bar takes no prop so every mount gets the identical control, and useChatContentWidth is the precedent. So useChatViewToggle reads and writes useChatViewStore, and the bar stays prop-free.

Three routes for the delete, no new table, no migration. The delete returns the whole row so the client can put it back; the restore takes that row and re-inserts it with the same id.

What the code already has, and what it does not

  1. No per-message delete exists anywhere. DELETE FROM llm_history appears only in migration tests (migration.zig:3966, migration_128.zig:179). There is no route, no handler and no API function. The only message-level writes are updateToolResultById and setToolResultImageUrl, both internal to the loop.
  2. The grouped view does not draw every row. Three of the first nine rows in this session are assistant rows with an empty response_content and only tool_calls_json. messageGroups filters empty groups, so they render nothing at all. That is the case for the toggle: you cannot delete a row the transcript never drew.
  3. The Context column needs a column that is not on the wire. getSessionMessagesSorted does not select is_feed_to_llm, and SessionMessage has no field for it. Both need adding before the raw view can show whether a row is still fed to the model.
  4. The "drop from context" half already works. is_feed_to_llm was added by Migration 5 (migration_5.zig:15) and getLLMHistories already filters on it at get_llm_histories.zig:63. markHistoryNotForLLMRun.zig:12 sets it to 0 for a whole session. Per-row is the same UPDATE with a narrower WHERE.
  5. A group is not a row. ChatMessageRow.vue draws one MessageGroup per scroller item and a group holds group.messages, which can be several llm_history rows. The action button has to hang off the message item, or three identical rows share one delete.
  6. Tool calls pair across rows. An assistant row's tool_calls_json holds call ids; each tool row's tool_call_id matches one. In this session every assistant row has exactly one call and one result, so deleting either side orphans the other.

Not on this page, and why

Raw as the default

The grouped view stays the default. Raw is for operating on rows, not for reading a conversation: a table of 18,001 rows is not a chat. The toggle remembers its value per profile, so anyone who wants raw keeps it.

Delete from here down

A range delete has to decide what happens to a tool call whose result is inside the range and whose call is outside it. That is a rule nobody will read, applied to a destructive action. One row at a time, and the pairing warning on each.

Edit a message

A different feature with a different risk: an edit silently changes what the model was told, and the reply below it was written against the old text. It needs its own design, not a second item in this menu.

A modal confirm

A modal covers the transcript, and the row you are about to delete is the one thing you need to see. The inline bar keeps it on screen and keeps the question next to its subject.

A hover-only trash icon

Unreachable by keyboard, invisible on touch, and a misclick farm in a transcript you scroll with the pointer. The button is always in the DOM at 35% opacity and comes to full strength on hover or focus.

Deleting a row that is still streaming

While is_loading = 1 the writer owns the row and will overwrite it. The button is disabled with that reason rather than racing the loop.
