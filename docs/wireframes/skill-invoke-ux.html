Manual skill invocation — better UI/UX

How I read the ask: when a human types /skill-<name> (or a bare /<name>), the composer, the transcript and the user-pill rail should all tell them which skill was invoked, how big it is, and what it cost — and the human's own words must stay the loudest thing on screen. Today the server appends the whole skill body as an XML envelope to the message text (src/agentic_loop/slash_skill_expand.zig:150) and the transcript echoes it verbatim (ChatView.vue:3956, a whitespace-pre-wrap bubble). Nothing is broken — it is just unreadable, and this page proposes the pixels that fix it. Wireframe only: no product code is touched.

These rules apply to **unit tests**. Other test layers (integration, end-to-end, consumer-driven contract tests at service boundaries) have different goals and are out of scope here. Do not tell the user those are wrong. ## When to Use Load this skill when the user asks you to write, add, improve, review, refactor, or fix unit tests, test coverage, flaky tests, or mocks — in any language or framework (pytest, Jest, Vitest, JUnit, Go test, Rust, RSpec, xUnit, etc.), even if they never mention "behavior" or "deterministic". ## Core practices - **Test through the public interface.** Don't test private methods or reach into internal state. If a private helper seems to need its own test, it is either covered through public behavior or it is a separate unit that deserves its own public interface. - **Assert outcomes, not mechanics.** Observable outcomes are return values, state visible via the public API, output written to a fake, and errors surfaced to the caller. - **One behavior per test.** Several assertions are fine if they describe one outcome. - **Name tests as behavior sentences**: `rejects_order_when_stock_is_insufficient`, not `test_order_3`. - **No hidden inputs.** Inject or seed every source of nondeterminism at the boundary: clock, RNG, network, filesystem, env, ordering, locale, shared state.
