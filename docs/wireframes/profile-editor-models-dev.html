Why this is simpler and not just shorter

  • Nothing is removed. All 7 advanced fields still exist and still write the same JSON keys. They just stop being the default thing you stare at.
  • The context window stops being a user responsibility. max_capacity_tokens stays null for this profile and resolves at read time — so a catalog refresh fixes every profile at once instead of leaving stale hand-typed numbers behind.
  • Override = type something. Empty field ⇒ inherit. That is exactly the existing null-vs-value model on the wire, so no config migration and no new sentinel.
  • Unknown model degrades honestly. Free text with no catalog hit ⇒ the strip says unknown model — set the context window manually and the compaction line shows the built-in 200k, which is today's behaviour.

Decisions to confirm before implementation

D1 — where the catalog lives

Recommend: runtime fetch + on-disk cache, backend-owned. One module (model_catalog.zig) owns load/refresh/lookup, mirroring session_llm_config.zig's "one owner" rule. Alternatives: bundling a 2.3 MB trimmed snapshot in git (works offline, rots, huge diffs on every refresh), or frontend-only fetch() (no server-side compaction gain — the bug stays).

D2 — when we refresh

Recommend: an explicit "Refresh catalog" button in Settings (General), plus a stale badge. Never at boot — a desktop app that silently phones home on every launch is a smell, and CI must stay hermetic.

D3 — the orphaned top-level compaction defaults

Recommend: put one "Compaction" block back in Settings → General (threshold %, optional forced context window), and make it the single global home for D3's cascade step 3. The alternative is deleting max_capacity_token_model / compaction_threshold_percent from the cascade as dead UI — but workspace overlays and hand-edited configs already use them.

D4 — model entry stays free text

Recommend: combobox, not a select. A strict dropdown would break self-hosted endpoints and the opencode.ai/zen URL in the screenshot, which is not what the catalog says. Unknown ⇒ show the honest "set it manually" state.

D5 — do we surface output cap + price?

Recommend: show both as read-only facts now; add max_output_tokens as a real profile field only if you want it. Pricing goes stale and is per-provider — it is information, not configuration.

D6 — workspace scope

Workspace settings can override profiles_models. Does a workspace get its own catalog cache (per-owner path), or does every scope read the one machine-wide cache? Recommend: one machine-wide cache — it is model metadata, not user data.

What changes on the wire (nothing, deliberately)

  • max_capacity_tokens / compaction_threshold_percent / thinking_budget_tokens stay number | null. Empty field ⇒ null, never "" — an empty slice binds as SQL NULL in this codebase's SQLite contract, and a cleared override must round-trip as null.
  • The catalog never writes into a profile. It supplies defaults at the four resolution points the backend already has (maxCapacityForModel, compactionThresholdPercent, the thinking/effort gates, the base-URL fallback). A catalog refresh therefore fixes every profile at once.
  • No config migration. An existing config.json is byte-identical after this change; only the resolved values differ (correctly, for non-MiniMax models).

Open risk

  • Offline / air-gapped. First run with no cache ⇒ catalog absent ⇒ every profile falls back to today's 200k built-in. The plan must make that state visible in the UI ("catalog unavailable — context window is the 200k built-in") rather than silently keeping the wrong number.
  • Provider/model ambiguity. deepseek-flash exists under several providers with different context sizes (DeepSeek's own vs opencode-go's). The resolution needs the provider, not just model — so a bare model name picks the highest-ranked match and the UI names the choice.
  • Upstream trust. A wrong limit.context upstream silently changes when pabrik compacts. An override that the user typed must always win, and the resolved source must be shown next to the number.
