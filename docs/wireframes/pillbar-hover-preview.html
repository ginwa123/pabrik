Pillbar hover preview — why the box is a 34px sliver

Task task_1792162810941_3 · worktree worktree/ffix-the-pillbar-hover-1792162799691 · source UserPillRail.vue:186 · shipped by PR #953
report + screenshot→ measure the box (this wireframe)→ pick a variant→ patch UserPillRail.vue→ functional UI test

PR #953 added a styled preview box that opens when a pill is hovered. It never looked right for a reason nobody could see: jsdom has no layout engine, so the spec suite that shipped it could only assert that the element exists — never how wide it is. The two defects below were found by rendering the component's real markup with its real CSS in a browser and reading getBoundingClientRect(). Both are in the same seven declarations.

1Two defects, not one

D1 — the box shrink-to-fits against a 32px containing block

The rule sets max-width: 280px but no width. An absolutely positioned box with left: auto and no width is shrink-to-fit, and its available width comes from its containing block — which is the rail's own padding box, 32px wide (right: 18px + padding: 8px 4px + a 24px pill). max-width is only an upper bound, so it never binds: the box comes out at the rail's own scale instead of 280px — 32–34px in the measurements below, and the exact used width even drifts with the hovered text, because a shrink-to-fit width is content-dependent.

This is the sliver in the report. The message text is /skill-behavior-unit-tests, and overflow-wrap: anywhere lets it break after every single character — the box renders /, s, k … one character per line, then hides the rest behind the clamp.

D2 — the box is anchored a full box-width too far left

right: 0 already puts the box's right edge at the rail's right edge. Then translate(-100%, -50%) moves it a further its own width to the left. The gap between the pill and its own box is therefore boxWidth − 24px — the anchor is a function of the box's width, which is why nobody noticed it.

today, at 33.7px widegap 9.7px — looks fine
after fixing D1 onlygap 256px — flies to mid-transcript

D1 and D2 cancel out. Fix the width alone and the box jumps ~256px away from the pill it belongs to — a new bug, worse than the one reported. Any acceptable fix has to move the anchor and the width in the same change.

4The candidate patches

V3 — RECOMMENDED · two declarations, same parent, same top math

// src/apps/desktop/src/components/chat/UserPillRail.vue:186
 .user-pill-message {
   position: absolute;
-  right: 0;
-  transform: translate(-100%, -50%);
-  max-width: 280px;
-  margin-right: 8px;
+  /* Anchor to the rail's LEFT edge: `right: 100%` is 100% of the rail's own
+     32px width, so the box's right edge lands `margin-right` left of the
+     pills. `right: 0` + `translateX(-100%)` counted the offset twice. */
+  right: 100%;
+  transform: translateY(-50%);
+  margin-right: 8px;
+  /* An explicit width. With `left: auto` and no width the box shrink-to-fits
+     against the rail's 32px padding box and collapses to ~34px. */
+  width: max-content;
+  max-width: 280px;
 }
Why this one. It repairs both defects, keeps the box a child of the rail — so pillCentreTop's calc(var(--pill-pad) + i * var(--pill-pitch) + var(--pill-h) / 2) still reads the one copy of the stack geometry that lives on the rail — and it touches nothing outside the one rule. The keyboard-focus path, the key-guarded close, pointer-events: none, aria-hidden and the 3-line clamp are all untouched.

Residual, stated honestly: under a ~340px pane a 280px box hangs up to 19px past the pane's left edge (measured: 19px at 320px). It cannot be clamped in CSS from inside the rail, because 100% in a max-width would resolve against the rail's 32px, not the pane. Accept it, or take V2.

V2 — fully adaptive, at the cost of the single source of truth

// the box renders as a SIBLING of <nav class="user-pill-rail">, inside the
// messages wrapper — so its containing block is the wrapper, not the rail.
 .user-pill-message {
   position: absolute;
+  right: calc(var(--rail-right) + var(--rail-w) + 8px);
+  transform: translateY(-50%);
+  width: max-content;
+  max-width: min(280px, calc(100% - var(--rail-right) - var(--rail-w) - 16px));
 }
Only this variant survives a 320px pane intact (252px box, fully inside). The price: the box leaves the rail's subtree, so it no longer inherits --pill-h / --pill-gap / --pill-pad — those have to be restated on the new parent (or the top math has to become measurement-based, which the component was deliberately built to avoid). The box would also be rendered by the host (ChatView) instead of by the component, moving state that currently belongs to the rail. Bigger diff, real drift risk, for a case that only bites below ~340px.

V1 — must not ship

Adding width: max-content and nothing else turns the 2-character sliver into a legible 280px box that is 256px away from the pill that opened it, overhanging the pane's left edge by 267px in a narrow pane. It is the shape of bug that looks like progress in a wide-pane screenshot.

6Decisions I need from you

  1. V3 or V2? I recommend V3: two declarations, one file, the component's architecture and its single-source-of-truth geometry intact. It leaves a ≤19px left overhang below a ~340px pane; V2 removes that but restructures where the box lives.
  2. Is the ≤19px narrow-pane overhang acceptable as a follow-up? If not, take V2 now — it is the only variant measured to fit at 320px.
  3. Keep -webkit-line-clamp: 3? At 280px a typical pill preview fits in 1–2 lines, so the clamp only ever bites on a pasted wall of text. 3 is a reasonable ceiling — say the word if you want 4.
  4. Ship the functional UI test with the patch? Without it, this exact defect can come back through any stylesheet edit and no unit test will notice.
