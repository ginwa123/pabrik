A dev tool terminal in the footer

The terminal already exists, but it is stranded in one chat's right sidebar. The footer is where a person looks for a tool that belongs to the window rather than to one conversation. This is the wireframe: a footer affordance, a dialog that lists the live sessions by workspace, and one click that turns a listed session into a working terminal.

Wireframe and plan for card task_1792513552823_0, pabrik, docs/wireframes/dev-tool-terminal-footer.html, 2026-10-20. Every measurement below was read out of a real browser against a real backend on port 8080 with its own HOME, at commit 969952c5d. The live server on 8081 was not touched.

footer button → dialog: sessions by workspace → pick one → the dialog is the terminal

1What is there now

Pabrik has a working terminal today. It is a tab in the chat's right sidebar, next to Explorer and Changes, and it belongs to one chat: its sessions are persisted under the localStorage key pabrik-terminal-sessions:<sessionKey>, where the key is the chat's own id, and the chips are numbered term 1, term 2 by a counter that lives in the browser tab.

That is the right behaviour for a terminal that belongs to a conversation. It is the wrong behaviour for the thing this card asks for, which is a terminal that belongs to the workspace and can be opened without a chat at all.

2The scope is the workspace, not the chat session

The card says a session-free terminal, and the clarification is that it is precisely workspace scoped. That single word decides the whole design, and it lines up with what the server already does.

What workspace scope means, checked against the source and a live backend
QuestionAnswerEvidence
Does a terminal need a chat session? No. POST /api/terminal/sessions {workspace_id, cwd} Created term-4 on the probe backend with no session anywhere in the request. It answered, and its output came back on the poll endpoint.
Does it need a workspace? Under --saas, yes, and the server refuses without one. terminal_guest.zig:46-52 routeFor returns .refuse with "SaaS mode runs the terminal inside the workspace VM: pass workspace_id" when the id is missing. In local mode the same request is answered with a host shell.
Is the chat the right persistence key? No. It is the wrong key for a workspace-scoped tool. TerminalTab.vue:63 The key today is pabrik-terminal-sessions:<chatId>. A workspace-scoped terminal is keyed by workspace, so the same shell is found from any chat, and from no chat.
Where does the label come from? Nowhere. The server never sees it. TerminalTab.vue:365 term 1 is a browser-side counter. Two chats both have a term 1, and neither can be told apart in a list that spans workspaces.

The one thing this scope buys

A workspace-scoped terminal is the only shape that survives the three things a person actually does with a shell: start it in one chat, walk away, come back to a different chat, and find it. Today the only way to reach a shell is the chat that started it, on a window at least 1024px wide, in a sidebar that is one of three tabs.

4What the server has to grow

This is the part of the card that is not only a picture. The dialog lists sessions that span workspaces, and the server does not serve that list today. Three things have to change, and they are small.

The backend delta, in the order it has to land
ChangeWhereShape
Store the workspace on a host session. terminal_session.zig:288 Add workspace_id: []u8 to Session and set it in createSessionPosix, exactly as terminal_guest.zig:100 already does for the guest path. One field, one assignment.
Give the registry an iterator. terminal_session.zig:343 g_sessions is a StringHashMap behind a mutex with no way to walk it; only sessionCount() exists. Add a listSessionsForOwner that copies the owner's rows out under the lock.
Serve the list. http_routes.zig:112 GET /api/terminal/sessions, owner-scoped from the session cookie. The route must be registered before the :id siblings, and the existing 404-on-foreign rule means a caller cannot see another user's rows.

Two decisions this wireframe makes, and one it leaves open

The list comes from the server, not from localStorage. The browser's pabrik-terminal-sessions:<chatId> map knows only the sessions this browser started in this chat. A footer that lists sessions "per workspace" has to know about the session a colleague's tab started, and about the session that outlived the chat it was started in. Only the server's registry knows that, and it already reaps the abandoned ones.

The label stops being invented in the browser. term 1 is a per-tab counter today, so two chats both have a term 1 and neither can be told apart in a list that spans them. The server already mints ids (term-1, term-2, and gterm-… for guests), so the list shows a short label derived from the id, and the workspace is the disambiguator.

Open: does the footer also replace the sidebar's Terminal tab? The wireframe keeps both, because the sidebar tab is scoped to a chat and the footer is scoped to the workspace, and the two answer different questions. If the review prefers one surface, the sidebar tab is the one to cut, and the right sidebar's hidden lg:flex is then the reason to cut it in favour of the footer.

The two things the tests will not catch

Owner scoping. Every list must be filtered by the session cookie's user, and there is no test today that asserts a second user cannot see the first user's sessions. The existing 404-on-foreign-session rule is the model to copy, and it deserves its own case.

The 20-session cap, seen from the window. The host cap is 20 and a VM's cap is 8 ttys. A footer list can show a user more live sessions than any one chat could hold, so the list has to show the cap as a count, and the "New terminal" button has to refuse with the server's own message when the cap is reached.

7Open questions

Does the footer replace the sidebar's Terminal tab?

Drawn as both, because the sidebar tab answers "what is running in this chat" and the footer answers "what is running anywhere in this workspace". If the review wants one surface, the footer should win, because the sidebar's Terminal is invisible below 1024px and the footer would not be.

Should the dialog open a terminal, or only list them?

Drawn with a "New terminal" button that starts a shell in the workspace that owns the selected group, and with the list rows opening an existing session. The alternative is a read-only list that only attaches, which is one button less but means a person with no session has to go back to a chat to make one.

What about a session whose chat is gone?

Drawn in the list, as a row under its workspace that reads exited (0) with the time it died. A session outlives the chat that started it, which is the whole reason the footer is worth building, so the list has to show the dead ones, or it will look like the app lost something.
