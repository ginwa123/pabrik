1 Elapsed chip next to every spinner CORE ASK

The spinner stays exactly where it is — SessionSlider.vue is untouched. A chip is added beside it reading 4m 12s: how long this worker has been running.

Two numbers, two meanings, both shown:

  • Elapsed — now - worker.created_at. "How long has this run been going?"
  • Last activity — now - worker.last_activity_nano. "Is it still doing anything?"

A worker can be 20 minutes old with a 2-second-old heartbeat (a long tool call), or 3 minutes old with a 9-minute-old heartbeat (stalled). Today both look identical.

2 Amber "stale" state CORE ASK

When last_activity is older than 5 minutes the chip turns orange and the row's last-activity text turns orange too. That is the same threshold family the backend already enforces: cleanup_stale_worker.zig deletes a worker row once last_activity_nano is older than 600s.

So amber means "this run is alive in the DB but has not heartbeated in 5 minutes — it is about to be reaped." That is the single most useful thing a user can know, and today there is no way to see it.

3 One shared formatter, three shapes

All chips come from one pure helper so the sidebar, the kanban card and the dialog can never disagree:

under 60s → 42s under 60m → 4m 12s 60m and up → 1h 04m 24h and up → 2d 3h

Mirrors the existing formatElapsed in SpawnSubAgent.vue (which already renders 12s / 1m 03s for sub-agents) — same buckets, same padding, promoted to a shared helper so the two surfaces match.

4 Sidebar rows keep their existing right-side slot

ChatsList.vue already hides the relative-time pill while processing (v-if="!isProcessing(item.id)") and shows the spinner instead. The chip takes that same slot, so the row never grows a second trailing element and the layout does not shift.

Idle rows are unchanged — still 12m / 2h from formatRelativeTime. Only running rows gain the chip.

5 Kanban: the rail and the label finally agree

Today KanbanTaskRow.vue paints a yellow 3px rail but renders the text ● agent running in muted grey, while WorkspaceItemTaskCard.vue uses a yellow CSS spinner. Three surfaces, one state, two colours.

The wireframe adds the elapsed chip to the card header and a last activity Xs ago segment to the metadata line, and tints that segment amber when stale. The rail stays yellow — it is the row's identity, not a warning.

6 Task detail dialog: the disabled button explains itself

KanbanTaskDetail.vue disables Start agent when a worker is running, with a tooltip that says only "wait for it to finish". The wireframe adds a Status row with the elapsed chip, a Last-activity row, and folds the elapsed time into the disabled item's own sub-label — so the reason is visible without hovering.

7 Chat app bar: no chip here REMOVED

The app-bar copy of the chip is gone — the title strip is back to title · sidebar toggle · ✕. The elapsed time still rides on the sidebar rows, the kanban rows/cards and the task-detail dialog, which is where the worker's state is already stated; repeating it in the bar crowded the title and the two window controls.

8 A second provide key, not a wider boolean NEW STATE

processingState is a Ref<Record<string, boolean>> injected by App.vue and read by eight components. Widening it to carry timestamps would touch every one of them.

Instead App.vue provides a second, additive key — workerActivity: Ref<Record<string, { startedAt: number; lastActivityAt: number; description: string }>> — populated from the same SSE handler and the same GET /api/workers bootstrap. Components that only need the boolean keep injecting processingState and are untouched; the chip opts in.

One shared <WorkerElapsedChip session-id="…" /> component reads the new key, owns the 1s ticker, and renders nothing when the session is not running.

9 One caveat worth deciding before implementation OPEN QUESTION

worker.last_activity_nano is only refreshed by updateWorker — the upsert touchCheckpointWorkers calls once before the loop and once per iteration (workflow.zig:795, workflow.zig:847). A single long tool call therefore leaves the heartbeat frozen for its whole duration, which would show a healthy worker as amber.

llm_history.updateWorkerActivityWithDescription exists and writes both the timestamp and a description, but has no production caller — only tests and comments reference it. Wiring it into the tool-call path is what makes "last activity" mean what the label promises, and it is the one backend change this feature needs.

Data source & refresh

Everything the chip needs is already on the wire — no new endpoint:

  • GET /api/workers returns last_activity (unix seconds, aliased from last_activity_nano), last_activity_description and created_at per row — worker_list.zig:53.
  • The SSE worker_updated payload already carries last_activity and last_activity_description — sse_send_event_worker.zig. The frontend's WorkerEvent type already declares both.

Refresh: the chip ticks locally every second from the last value it was given (no polling), and re-syncs whenever a worker_updated event lands or App.vue's existing fetchInitialWorkers re-runs on SSE reconnect. created_at is a SQLite CURRENT_TIMESTAMP string, so it needs the same UTC-normalising parse formatTaskTimestamp already does.

Backend change needed: one — call updateWorkerActivityWithDescription from the tool-call path so the heartbeat tracks real activity (see note 9).
