The kanban add-task and task-detail pages

One component renders both, in one long column, with three exits and a picker that covers the controls under it. Here is the same surface read as a task document plus a run-settings rail, with its own URL.

Wireframe and plan for card task_1792222407646_1 ("revamp the design when add task or task detal"), pabrik, docs/wireframes/kanban-add-task-and-detail.html, 2026-10-17. Every number below was measured in a real browser against KanbanTaskDetail.vue at 1440x900 on the harness's own backend, never on the live server.

What is there now

KanbanTaskDetail.vue is one component with a mode prop, hosted by KanbanView.vue inside a full-cover panel. Create mode is local state only: no URL param, so a refresh, a share or a new tab cannot reach it, and Back leaves the board instead of closing the form. Detail mode does have a URL (?detail=<taskId>), so the two halves of one surface disagree about where they live.

Three defects worth fixing first

1The picker covers its neighbours

The Skills list is absolutely positioned inside the scrolling body, so it cannot be anything but clipped to it. It hides both switches and the bottom third of what it lists. A picker that opens in place, moving the rows below it down instead of lying on top of them, cannot do this at any viewport height. Both behaviours are drawn below, measured the same way.

2Create mode has no URL

The URL is byte-identical before and after opening the form (measured: empty query both times) while the detail panel carries ?detail=. You cannot share a half-written task, refresh one, or open it in a second tab, and Back abandons the board instead of the form.

3Three exits, one meaning

Back, the cross and Cancel all emit the same close, and in create mode Back is a lie: there is no previous screen. Keep the cross and Cancel, drop Back, and let the browser's own Back do the job once the view has a URL.

The add view gets its own URL

The app already draws this line: something that replaces the main view owns a path (/app/{ws}/doc/{id}, /app/kanban/{itemId}/settings), while an overlay of the board rides a query param (?detail=, ?prs=). The add-task page replaces the board, so it belongs in the path.

/app/ws_1/projects/item_7 identical before and after opening the form

/app/ws_1/projects/item_7/add?column=col_1
  • The route is registered before the catch-all, and before the /projects/:projectId entry.
  • buildAppUrl gains an addTask target and parseAppPath gains a projectAdd kind. Without that second half /add falls through to { kind: 'other' }, useCurrentMainView answers none, and the sidebar loses its active project row for the whole page.
  • Opening the form pushes the path, so Back returns to the board and closes it, exactly as ?detail= already does; closing it replaces back to the board URL.
  • The target column rides ?column=, so a shared link opens on the same column without a second path shape to parse.
  • The four places a new path shape must be taught are listed in the plan, including the trailing-slash normalisation in detectLegacyAppUrl, which only fires once isAppPath knows the shape.

The gate, and what I defend

Both scanners were run from the repo root against this file after every edit. The source linter is clean, and what remains from the inspector is what a spec document cannot honestly satisfy without faking the thing it documents.

Clean

lint.mjs reports 0 FAIL, 0 WARN. inspect.mjs cleared everything it flagged on the first draft: four interface fragments of 300 by 200 or more where it had counted one, no horizontal overflow at 1440, 768 or 390, the four 4.4:1 contrast warnings, the missing first-screen button, and the two rows of identical cards at 390.

Defended: no motion

still-page counts 0 moving elements and asks for eight. This page documents a motion-free interface, and adding entrance animations to please the meter would fake the very thing it documents.

Defended: no photographs, no footage

no-real-pictures and no-footage want photographs and a clip. The subject is a form inside this app, and the honest pictures of it are the interface fragments the skill counts for software. There is no film of a task being typed.

What the wireframe itself measures

Loaded in a real browser and read out of the DOM, not eyeballed. The four fragments are 1120 wide and 823 to 940 tall, and the page never scrolls sideways. In the first pane the open picker overlaps each of the two rows under it by 25px and its bottom sits 151px past the card's box. In the second, opening the picker pushes the rows below it down 183px and overlaps them by 0. The magnitudes differ from the app's because this is a mock; the mechanism is the one the probe measured on the real component.

Open questions

Which action is the big one?

Drawn as Create task primary with run-agent beside it. Today it is the other way round because Enter runs the agent, and that is a decision to re-take rather than a bug. If the answer is to keep run-agent primary, the two flat buttons simply swap order and the caret still goes.

Do the skills chips live in the rail?

Drawn in the rail, under the picker. They are what you check before committing, so they belong next to the switch that decides how far the agent goes. The alternative is the left column beside the other tags, which reads as task content rather than run configuration.

Is /add worth the four touchpoints?

The cheap version is ?add=1 on the board URL: one file, no route work. The path is what makes Back mean "leave the form" and stops the add page borrowing the board's identity. The card asked for /add, so the plan does the path, and the plan names the fallback in case review disagrees.
