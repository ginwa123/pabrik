Wireframe — a Pull request / Merge request button on the kanban board

Card: “add a button pull request or merge request in kanban” — “for now just a button to get list pull request and close request”. Read as: one board-level button → a list of the repo’s open PRs/MRs → close one from that list. v1 is list + close; everything else is named in §7. Nothing here is implemented — this is the artifact for approval.

kanban board→ button in the board header→ PR list view→ Close → confirm→ row leaves the list, card badge flips
live states tab close

§1Where the button lives

The board header already carries six controls. The new one is a board-level action, so it belongs with them — and the board already knows its repo (item.path), which is the whole reason a PR list can be asked for at all.

Annotations

  1. Label is forge-aware, never hardcoded. Text comes from helpers/forgeWording.ts — “Pull requests” on GitHub, “Merge requests” on GitLab. A GitLab user reading “Pull requests” is the same class of bug that module was written to kill.
  2. The count is open change requests only (the same number as the forge’s own “Pull requests 8” tab, which matches this repo today). It is '' — no badge — until the first fetch answers; it is never a fake 0, because “0 open” and “we could not ask” must look different.
  3. Icon is UiIcon name="pr" — the name already exists (components/ui/icons.ts:157). No emoji anywhere in this surface: the button, the rows and the dialog all render inline SVG or the allowed typographic set (↗ ↻ ✕ ⋮ ⚠).
  4. The button is disabled with a visible reason, not a tooltip, when the board has no project root (item.path is null — legacy boards; the yellow “Set project root” banner already handles that case) or when the forge has no CLI (generic provider). A mute greyed button is how a user learns nothing.
  5. Width honesty: the header is flex-wrap: wrap already, and the density toggle only renders in row mode. Adding a labelled button costs ≈120px at the 280px side-panel widths this app runs at. If it wraps badly, the fallback is icon-only + count with the label in title — decided by measurement, not taste.

Notes on the list

  1. The forge is named in the header, and in the verb of every action. “Pull request” / “merge request”, “Close” / “Close”, via gh / via glab — all from forgeWording(), with the forge mark from the existing ForgeIcon.vue. Nothing in this surface hardcodes GitHub prose.
  2. The board join is the reason this belongs in kanban rather than in a browser tab. Every card already carries task.git_branch, and this repo’s PRs are opened from exactly that branch (worktree/<slug>-<ts>, verified on the 8 open PRs today) — so the match is exact, not fuzzy. It is a client-side join against item.tasks: no extra request, and it works while the list is loaded. The badge names the column too, so the row says where that work sits.
  3. “no card on this board” is a first-class row, not a filter. A PR whose card was deleted, or that predates the board, is exactly the kind of thing you want to find and close — the reason a board-scoped list would be worse than a repo-scoped one.
  4. ⚠ conflicts reuses the vocabulary the card badge already speaks (isPrConflictValue() in prStatusCache.ts: GitHub CONFLICTING/DIRTY, GitLab CONFLICTED/NOT_MERGEABLE). One conflict rule for the whole app, or the row and the card will disagree.
  5. Close is the only write in v1, and it is the quiet colour — outline red, never a filled primary. The filled button in this app means “the thing you came to do”, and coming here means looking.
  6. Merge is deliberately absent. It shipped on the PR tab (MergeBox.vue, POST /api/git/pr/merge — PR #895) with a review of merge state, head sha and the delete-branch decision in front of it. A bare “Merge” in a list would be a second, weaker door onto the same write. The row links to the board instead.
  7. “Only this board” is a filter, not a second request — the join is already in memory. Default on is the honest default for a board surface: you came from the board. The count is stated (5 of 8) so a hidden row is never a mystery.
  8. Loading, empty and error are three different pictures. This is the whole point of the Effect-TS rule: the state comes from a typed Effect<A, PrListError>, so “no open pull requests” can never be what a failed gh call looks like. Empty states say who answered; error states say what failed and what to do.

Annotations

  1. ‹ Back to board drops ?prs= with router.replace, so browser Back and this link do the same thing.
  2. The tab strip is the only view state here worth a URL param, and it uses the same one as the view: ?prs=open|closed. A local ref for it would be a house-rule violation — refresh and Back/Forward have to restore the tab.
  3. ↻ Refresh is manual in v1 (D5). The PR tab’s 30 s poll is not inherited: a table of repo-wide PRs is not worth a subprocess every 30 s while it is open.
  4. “New pull request ↗” links out — creating one already exists in the task chat (CreatePrDialog, opened from ChatView.vue:6130), and that one knows which worktree and base branch it is creating from. This button must not become a second, dumber form (D4).
  5. Row actions are two hits: ↗ (open on the forge) and Close. No kebab menu — a menu for two items costs a click and hides the destructive one.
  6. The confirm dialog reuses dialogs/ConfirmDialog.vue (Teleport, backdrop, Esc) and names the branch, because “close” is a write on a remote and the branch is what ties it back to a card here.
  7. data-testids are drawn where they belong: kanban-view-<itemId>-pr-button follows the existing board-header convention; row ids (pr-row-893) make the close flow assertable without a live forge.

§3The close flow, step by step

Close is a write on a remote with other people’s reviews on it. Four things must be true before the button is live, and the fourth is the one that keeps the board honest.

StepScreenWhat happens
1Row → Close Nothing is sent. The confirm dialog opens with the PR name, repo, head → base and the sentence “the card does not move columns”.
2Confirm → Close pull request The row enters a closing state: the Close button becomes a spinner, every other row’s Close is disabled, the dialog stays until the answer arrives. Esc / backdrop / Cancel abort before the request; after it, no — the request is already out and a cancel button that cancels nothing is a lie.
3Answer POST /api/git/pr/close returns a re-read of the forge’s status, not an exit code (§6). closed: true → the row leaves the Open list. closed: false + detail → an error banner with the forge’s own sentence and Retry; the row stays where it was.
4After Toast (Closed #893 · worktree/…), the open count drops by one on the board button, and the card’s branch badge flips to “PR closed” immediately — one invalidatePrStatus(cwd, branch) call, because the shared cache has a 60 s TTL and the user just watched the thing change.

After a close — the row is gone. Where did it go?

Open 7 Closed 901 just now: #893 closed
The Closed tab is one flag on the same request — and without it a close is indistinguishable from a row that vanished. That is why it is in v1 (D3), not deferred.

Annotations

  1. No optimistic removal. The row stays until the forge says closed. A list that drops the row on click and re-adds it on failure teaches the user to distrust the list.
  2. No auto-move of the card. The board’s own contract says only a human moves a card into merged, and that question was already answered “no auto-move” on the merge box (task_1791718426390_4). Closing a PR on the board moves nothing on the board.
  3. No --delete-branch in v1 (D6). The board’s branches are the session worktrees — deleting one from a list row would delete the directory an agent is standing in. The forge page still offers it.
  4. Errors are sentences from the forge, capped and trimmed by the same setFetchDetail discipline the status/merge handlers use. “gh exited 1” is not a message; “Pull request #893 is not open” is.
  5. The card badge invalidation is part of the change, not a nicety. prStatusCache.ts exposes only a test-only clearPrStatusCache() today; this work adds a per-key invalidation so one close does not nuke the board’s 30 cached branches.

§5URL contract and the one shared rule

URLMeansWritten by
/app/…/kanban/<itemId>board, nothing open—
?prs=openPR list, Open tabthe header button (router.push)
?prs=closedPR list, Closed tabthe tab (router.replace)
?prs=open&sorts=…&layout=rowssiblings untouchedthe existing board URL builder
?detail=<taskId>unchanged, unrelatedexisting
  • Opening the view is navigation → router.push, so Back returns to the board.
  • Switching the tab inside it is a view switch → router.replace, so it does not stack history.
  • The tab is read back on mount, so a shared link opens on the Closed tab.
  • A local ref for “is the PR list open” or “which tab” — unreachable by refresh, Back/Forward and shared links.
  • Dropping sorts/layout/detail when writing prs — the board already has a builder for exactly this reason.

The board join, precisely

  1. Row ← head_ref (GitHub headRefName / GitLab source_branch).
  2. Card ← item.tasks[].git_branch, exact string equality. No prefix matching: two cards whose slugs start alike must not both claim a row.
  3. Two PRs can point at one card (row #890 and #893 today are the same task’s plan and code) — the badge repeats, which is correct.
  4. No card → boardjoin.none: “no card on this board”, still closeable.

CLI facts — verified on this machine, 2026-10-12

  1. gh pr list: --state {open|closed|merged|all}, --limit, --head, --json with the full field list (number, title, url, state, isDraft, headRefName, baseRefName, author, updatedAt, reviewDecision, mergeStateStatus, mergeable, statusCheckRollup…).
  2. gh pr close {<number>|<url>|<branch>} [-c|--comment] [-d|--delete-branch].
  3. glab mr list: defaults to open; -c|--closed, -M|--merged, -A|--all, -F|--output json, -P|--per-page, -o|--order, -S|--sort. The state mapping is not symmetric: GitHub takes a value, GitLab takes one of four booleans — the argv builder owns that mapping, not the caller.
  4. glab mr close [<id>|<branch>…] takes no comment flag and needs no --yes (that trap was glab mr create). Hence: no comment field in v1 — a field that silently does nothing on one forge is worse than no field.
  5. Unverified, must be checked before the parser is written: the exact JSON key names of glab mr list -F json (machine’s GitLab token is absent, so it cannot be run here). Precedent for the risk: the alias-tolerant parse style of GlabMrView. Do not ship GitLab columns on an assumed field name.
  6. Route order: /api/git/pr/list and /api/git/pr/close are literals with no :param sibling under /api/git/pr/ — keep it that way (the comment at http_routes.zig:325 exists because the alternative silently changes which handler a path resolves to), and assert it by matching, not by grepping the source.
